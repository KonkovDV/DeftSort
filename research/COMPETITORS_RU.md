## 2. Разбор по репозиториям

### 2.1 `UBTECH-Robot/tk_sdk_demo`, пакет `grab_demo`: самый близкий прототип
- **Архитектура.** Три узла: `yolo_detect_node` (детекция и 3D), `grasp_executor_node` (state machine IDLE→MOVING→VERIFYING→PLACING)
  и `pose_node`. Мост между ними — свой тип `GraspCandidate.msg`. IK берётся из MoveIt2 `/compute_ik` (KDL, `avoid_collisions=True`,
  SRDF на 999 отключённых пар коллизий). Есть шаги с ручным подтверждением (`input()`), поэтому автономности нет.
- **Восприятие.** YOLOv8n (COCO, conf 0.5) и `ApproximateTimeSynchronizer` для цветного кадра и глубины. Глубина берётся в центре
  bbox, при нуле — медиана 3×3. `camera_info` используется для K. Точка переводится в `pelvis` через TF. Ориентация хвата —
  **константный кватернион, снятый через tf2_echo** (`[-0.187, 0.647, -0.562, 0.481]` для левой руки). Для правой руки он
  отражается относительно плоскости xz. Смещения хвата постоянные (`[-0.10, ±0.13, -0.05]` м).
- **Захват.** Только боковой, кисть закрывается до 0.55 (не до 0). Перед движением вызываются `SetForce(0.4)` (400 г) и
  `SetSpeed(0.3)`. Открытая кисть — 1.0 на пальцах, 0.0 на повороте большого пальца, как у нас.
- **Движение.** `cmd_pos`, spd 0.4 рад/с (у нас 0.8), `cur=5`. Финальный подход идёт на spd/3, подход к pre-grasp на spd/2.
  Есть **заготовленные промежуточные позы** prepare (локоть −0.9 → −2.5, рука поджата) и обратная последовательность для отхода.
  Если TCP ниже 0.1 м, выполняется полная последовательность, иначе сразу последняя поза. Это защита от стола.
- **Проверка.** После движения поза TCP сверяется по TF с IK-целью: порог 5 мм и 5°. Достижение суставов проверяется с
  допуском 1°, тайм-аут 7 с, после чего код идёт дальше без ошибки.
- **Нет:** проверки взятия, детекции выскальзывания, бюджета времени, восстановления после ошибок, пробирок.
- **Факты об интерфейсах, которые подтверждаются кодом.** `/arm/cmd_pos` с моторами 11–17/21–27 и тем же порядком суставов, что у нас.
  `/head/cmd_pos` (голова: pitch 0.3 вниз). Сервисы `/inspire_hand/set_force|set_speed/{left,right}_hand` (у организаторов они тоже
  есть, INTERFACES.md:67–68). На реальном роботе камера называется `/ob_camera_head/...`, в симуляторе — `/cam_head/...`. Значит, имя
  камеры **нужно параметризовать** под перенос на робота в Кронштадте.

### 2.2 `UBTECH-Robot/tiangong2pro_tf`
- Пакет `tiangong2pro_urdf`: xacro той же модели и **STL-меши** всех звеньев, включая `pelvis`, `waist_yaw_link`, плечи, локти,
  запястья, `L/R_base_link` и пальцы. Имена мешей совпадают с `package://tiangong2pro_urdf/meshes/...` в нашем `data/tiangong_pro_with_hands.urdf`
  (126 ссылок). Ориентация кистей (`left_hand_to_tcp rpy="3.14 0 -1.570796"`) совпадает с нашей.
- Нам это даёт возможность **офлайн** построить сферы по настоящей геометрии, а не по тензору инерции. См. идею I1.

### 2.3 `GlobalHumanoidRobotChallenge_2026_Baseline` и `GHRC_Evaluation_2026` (UBTECH, Walker S2)
- Другой робот с параллельным захватом. Основа — LeRobot (ACT, Pi0, SmolVLA): **тяжёлые модели, нам не подходят.**
- Скриптовый сбор данных `auto_collect/task_part_sorting.py`. Этапы approach (+0.25 м) → grasp (+0.01, wrist pitch −0.6) →
  lift (+0.20, pitch −0.2) → place (+0.18 над ящиком), затем проверка успеха и при неудаче повтор.
  **Позы деталей берутся из USD (`scene_builder.get_parts_world_poses()`), то есть из ground truth. По нашим правилам
  (TASKS.md, «Правила решения») это аннулирование.** Переносим только структуру.
- Свои места в ящике по типу детали (`place_offset` ±0.06–0.08 м по y), чтобы детали не ложились друг на друга.
- Порядок взятия задан: сверху вниз, потом слева направо.
- `DualArmIK`: pinocchio, взвешенный DLS (вес ориентации 0.1) и **нуль-пространство к нейтральной позе**
  (`dq += w·N·(q_neutral−q)`). После 30 неудач подряд warm-start сбрасывается.
- Тайм-аут на этап, сброс робота домой между эпизодами, settle 2 с после старта.

**Наши сильные стороны, которых нет ни у кого из них.** Восприятие только по датчикам, с RANSAC-плоскостью, сегментами по глубине
и венгерским сопоставлением с перечнем из `/sim/task`. Отказ от неуверенных объектов (штраф −10 больше выигрыша). Сертификация
swept-сфер против тела и стола. Синхронные суставы, которые в сумме дают прямую в пространстве суставов. Замыкание контура против

**Наши пробелы, которые закрывают идеи ниже.** Нет сенсорной проверки взятия и выскальзывания. Нет бюджета времени на один объект,
поэтому возможен −10 «в руке на тайм-ауте». Ящики берутся по номиналу из scene.yaml без проверки камерой. Все объекты кладутся в
центр ящика, то есть в стопку. Сферы тела сделаны по инерции, а не по мешам. Хват ничем не ограничен по силе. Нуль-пространства в IK нет.

## 5. Конкретные изменения (псевдокод и diff, в код решения **не внесены**)

### I1 + I4: проверка взятия по датчикам
```python
# node.py __init__
from geometry_msgs.msg import WrenchStamped
s.wr={};s.hs={}
for k,side in (('l','left'),('r','right')):
    s.create_subscription(WrenchStamped,f'/arm_6dof_{side}',lambda m,k=k:s.wr.__setitem__(k,m.wrench),qos_profile_sensor_data)
    s.create_subscription(JointState,f'/inspire_hand/state/{side}_hand',lambda m,k=k:s.hs.__setitem__(k,m),10)
# одна вызываемая при старте процедура: SetForce/SetSpeed (bodyctrl_msgs/srv), async, без блокировки >1 с
def held(s,side,f0):
    """True если объект в руке: прирост |F| к базе до захвата и/или пальцы остановились не дойдя до цели при effort>порог."""
    f=np.array([s.wr[side].force.x,s.wr[side].force.y,s.wr[side].force.z]);dF=np.linalg.norm(f-f0)
    h=s.hs.get(side);stalled=h is not None and np.mean(h.position[:4])>0.08 and np.max(h.effort[:5])>0.25
    return dF>0.5 or stalled          # пороги калибровать по v6+/Kaggle (не угадывать!)
# в pick_place: f0 = wrench перед закрытием; после q_lift:
if not s.held(side,f0):
    s.hand_open(side); s.go_home(side); return False   # объект не поднят -> 0 баллов, а не -10
# во время переноса (каждые 0.1 с): если held() стало False -> slip: не продолжать к ящику, домой, переснять сцену
```
Обоснование: в SCORING (уточнение 2 ноября) поднятый и оставленный вне ящика объект даёт −10. Детекция выскальзывания по F/T и

## 6. Возможные нарушения правил, которых избегаем
1. **GT-позы из сцены** (GHRC `get_parts_world_poses`, RoboMIND `task_check` через USD). У нас это аннулирование задачи. В решении
   их нет. В харнессе Kaggle — только `/sim/task/result`.
2. **Отладочные топики** `/sim/task/check`, `/sim/objects/randomize`, `/sim/objects/set`. На итоговой проверке обращения к ним
   фиксируются. Наш `node.py` их не использует. Проверить это надо grep-ом перед сдачей (тест A-*).
3. **Копирование кода.** Совпадения кода аннулируются, поэтому из `tk_sdk_demo` и GHRC ничего не копируем: другие команды тоже
   могли взять этот демо-код.
4. **Константы из scene.yaml (TRAYS, TABLE_TOP) и офлайн-априори размеров объектов (`priors.json`)** — серая зона. Это не позы
   объектов, но их нужно (а) подтверждать датчиками (I6, плоскость стола RANSAC уже есть) и (б) честно описать в README.
5. **Рука через тело.** Самоколлизии в симуляторе выключены, но траектории проверяют. Без I3 модель сфер приблизительная.
6. **Скорость.** В `cmd_pos` spd > 0.8 и 0 обрезаются до 0.8. Наша синхронизация (`spd = 0.8·dq/max dq`) корректна. Значения
   `spd ≤ 0.05` для почти стоящих суставов допустимы.
7. **ultralytics (AGPL-3.0).** Если когда-нибудь понадобится YOLO, нужна совместимая лицензия всего решения. Сейчас не используем.
